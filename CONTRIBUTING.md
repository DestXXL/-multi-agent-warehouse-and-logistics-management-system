# Совместная разработка

Принятый порядок совместной работы: отдельные ветки участников, согласование интерфейсов и интеграция через Pull Request. Этот документ уточняет практические шаги; он не вводит новые права доступа, обязательное число рецензентов или неподтверждённые правила защиты веток.

## Перед началом

Проверьте рабочую копию:

```bash
git status --short --branch
git remote -v
git branch -avv
```

Работайте в ветке, указанной для вашей задачи. Личная ветка участника №2 описана в [HANDOFF](HANDOFF.md) и не является общей веткой команды. Не создавайте и не переключайте ветку без запроса. Если есть изменения, сначала определите их владельца и способ сохранения. Не используйте сброс, очистку или автоматический stash как универсальное средство переключения.

Для новой копии используйте команду клонирования из [README](README.md). Ссылки `origin/codex/team-handoff` и `codex/participant-2-agents` относятся к прежней передаче и не являются текущей инструкцией. При синхронизации сначала прочитайте различия веток; не подменяйте это автоматическим merge или rebase.

## Границы ответственности

| Участник | Область по существующему плану |
| --- | --- |
| №1 | Модели склада, симуляция, проверки команд и API |
| №2 | Агенты, назначение, маршрутизация, координация и объяснения |
| №3 | Интерфейс, отображение состояния и интеграция |

Изменения участника №2 могут требовать согласованной правки вызовов в `simulation.py`. Распределение областей не означает запрета читать соседние модули и не доказывает персонального авторства. История интеграции приведена в [контексте №2](docs/participant-2-context.md).

Перед изменением общего JSON-контракта, фаз или семантики команд согласуйте затронутые backend, frontend и тесты. Не совмещайте самостоятельную задачу с форматированием чужого кода или переименованием API.

## Подготовка изменения

1. Опишите проблему и ожидаемое поведение, отделив уже реализованное от будущего.
2. Проверьте фактическую архитектуру и существующие тесты.
3. Выполните только согласованные изменения.
4. Запустите относящиеся к ним [проверки](DEVELOPMENT.md). Для поведения нужны содержательные сценарии; для документации – ссылки, команды и соответствие исходникам.
5. Проверьте `git status --short`, `git diff --check`, `git diff --name-status` и `git diff --cached --name-status`, затем содержимое diff. Обычный diff не включает untracked-файлы: прочитайте их отдельно. Отличайте ранее существовавшие изменения от внесённых в текущем задании.

Не добавляйте окружения, сборки, секреты и служебные данные инструментов. Не обновляйте зависимости ради редакторской задачи. При задании только на документацию итоговые изменения должны состоять исключительно из документационных файлов.

## Что включить в Pull Request

* Проблему и конкретное изменение поведения или документации.
* Затронутые контракты и совместимость, если они меняются.
* Выполненные проверки и результаты; отдельно – непроверенные условия.
* Известные ограничения и дальнейшие задачи, которые не входят в изменение.

Базу PR выбирают по фактической истории веток и договорённости команды. Не используйте удалённую ветку из старого документа без проверки её существования. Коммиты и публикация программным агентом выполняются только по прямому запросу пользователя; подготовленный diff сам по себе такого разрешения не даёт.

## Документация

Единый язык – технический русский; пути, команды и идентификаторы остаются оригинальными. В прозе используется тире «–». Синтаксические дефисы в командах, именах и Markdown не заменяются.

README содержит обзор и первый запуск; архитектура – механизм и API; DEVELOPMENT – процедуры; статус – готовность и дефекты; план – будущую работу. Не копируйте один и тот же подробный раздел во все файлы. У результатов проверки указывайте дату, коммит и окружение.

Лицензия пока не выбрана. Не добавляйте от имени команды условия распространения, гарантии безопасности или новые обязанности без основания.
