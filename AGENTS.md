# Инструкции для программных агентов

## Область действия и начало работы

Этот файл действует на репозиторий. Системные инструкции, инструкции разработчика и явная задача пользователя имеют приоритет.
Более конкретные инструкции действуют в своём поддереве. Перед изменением файла проверьте применимые инструкции на пути к нему.
Codex первоначально ищет проектные инструкции от корня проекта до текущего рабочего каталога, а не во всех вложенных каталогах.
В одном каталоге `AGENTS.override.md` заменяет `AGENTS.md`; дополнительные имена учитываются только при соответствующей настройке.
Обычная ссылка на Markdown не является механизмом автоматической загрузки или наследования инструкций.

Перед изменениями проверьте `git status --short --branch`, текущую ветку и существующие изменения.
Работайте в текущей ветке, указанной пользователем; не создавайте и не переключайте ветку без запроса.
Определяйте фактическое поведение по текущему коду и проверкам; старые отчёты, планы и статус могут устареть.
Читайте дополнительный контекст по задаче, а не весь комплект документации в каждой сессии.

## Карта проекта

* `backend/models.py` – dataclass-модели и JSON-представление.
* `backend/simulation.py` – состояние, резервы, водительские фазы, движение и события.
* `backend/agents.py` – детерминированный выбор исполнителя, BFS и набор перекрытий.
* `backend/layout.py` – Pydantic-модели статического макета и проверка связности.
* `backend/main.py` – FastAPI, один экземпляр симуляции, HTTP и WebSocket.
* `frontend/src/App.tsx` – диспетчерская и планшет; `LayoutEditor.tsx` – конструктор; `main.tsx` – выбор экрана.
* `tests/test_workflow.py`, `tests/test_layout.py` – проверки сценария и макетов.

Стек: Python 3.11+, FastAPI/Pydantic/Uvicorn; React 19, TypeScript, Vite. Не предполагайте наличие LLM, базы данных, автономных процессов роботов или физических интеграций. Контракты описаны в [архитектуре](architecture.md).

## Изменения и совместимость

* Выполняйте задачу пользователя, включая функциональные изменения, когда они входят в её объём. При работе исключительно над документацией не меняйте исходники, тесты, зависимости и конфигурации; обнаруженные дефекты описывайте отдельно.
* Сохраняйте существующие пользовательские изменения. Не сбрасывайте рабочее дерево, не удаляйте чужие файлы и не переключайте ветку с риском переноса незавершённой работы.
* Коммиты, push, merge, rebase и переписывание истории выполняйте только по прямому запросу пользователя.
* Сохраняйте контракт `Robot`, `robots`, `/api/robots/...` и водительские подтверждения, если изменение контракта не входит в задачу. Затрагивая общие API, учитывайте backend, frontend и тесты вместе.
* План и прибытие в точку не означают подтверждения забора/доставки. Проверяйте ограничения назначения, резерва, вместимости, фаз и занятости клеток. Не описывайте желаемые инварианты как уже полностью обеспеченные.
* Пользовательская геометрия может менять размеры и число ресурсов. Не закрепляйте в новой логике две машины или карту 12 × 8.
* Не подключайте внешнего планировщика и не меняйте алгоритмы под видом редакторской правки. Такой контракт пока является планом.
* Не сохраняйте секреты в репозитории. Не применяйте reset или новый макет к уже запущенной чужой демонстрации для проверки своей задачи.

## Стиль и проверки

Сохраняйте стиль затронутого файла: Python `snake_case` для функций, `PascalCase` для классов; TypeScript/React `camelCase` и `PascalCase`. Не выполняйте попутное форматирование. TypeScript настроен в strict-режиме; отдельный линтер не настроен.

Документацию ведите на русском, идентификаторы оставляйте как в коде. В прозе используйте тире «–»; синтаксис команд, имена и разделители Markdown сохраняйте корректными. Разделяйте «реализовано», «частично реализовано» и «запланировано». Ссылайтесь на существующие относительные пути. Не дублируйте историю сессий и команды запуска по всем документам.

Установка и запуск: [DEVELOPMENT.md](DEVELOPMENT.md). Команды из корня при установленном окружении; выбирайте нужные по характеру изменения:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
npm --prefix frontend run build
git status --short
git diff --check
git diff --name-status
git diff --cached --name-status
```

Для Linux/macOS используйте `.venv/bin/python`. При отсутствии окружения установите `backend/requirements-dev.txt`, а зависимости frontend – через `npm ci` в `frontend`. Не переустанавливайте зависимости ради небольшой правки Markdown. Команд `npm test` и `npm run lint` нет.

Для документационных правок проверьте ссылки, команды, соответствие коду и итоговый список файлов. Если проверка выявляет ошибку кода вне согласованного объёма, зафиксируйте её, не исправляйте молча. В отчёте укажите реально выполненные проверки, результаты и непроверенные сценарии.

Для документации не запускайте полный набор тестов и сборку без технической причины. Для поведения backend выбирайте относящиеся к нему тесты; для frontend проверяйте сборку и затронутый пользовательский сценарий.
Обычный diff не показывает untracked-файлы: отдельно прочитайте каждый новый файл и проверьте его назначение.
Просмотрите содержимое diff, а не только список путей. Отличайте свои правки от исходных изменений.
