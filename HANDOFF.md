# Передача работы участнику №2

Дата: 15 октября 2026 года.
Ветка передачи: `codex/team-handoff`.

## Что передаём

Работающий демонстрационный прототип управления складскими заданиями. Целевой пользователь — диспетчер и водитель погрузчика с планшетом. Сейчас движение моделируется; реальной техники и LLM нет.

Стек: Python 3.11+ / FastAPI / WebSocket; React 19 / TypeScript / Vite. Состояние хранится в памяти процесса.

Реализованы:
- Диспетчерская карта, каталог товаров, заказы, техника и журнал событий.
- Детерминированные менеджер, агент маршрута и агент зоны.
- Резервирование товара и выбор исполнителя по приоритету, расстоянию и условной вместимости.
- Планшет водителя с выбором погрузчика, своим маршрутом и следующим действием.
- Принятие задания, подтверждения забора и доставки с проверками на сервере.
- Сообщение о препятствии на собственном маршруте, обход или ожидание, открытие проходов диспетчером.
- Возврат на стоянку после доставки, чтобы освободить отгрузку.
- Блокировка команд при потере связи и синхронизация двух вкладок.

## Запустить и проверить

Терминал 1, из корня репозитория (macOS/Linux):

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements.txt
uvicorn backend.main:app --reload
```

На Windows: `py -3 -m venv .venv`, затем `.venv\Scripts\Activate.ps1` в PowerShell; остальные команды те же. Нужен Python 3.11 или новее.

Терминал 2:

```bash
cd frontend
npm ci
npm run dev
```

Откройте http://localhost:5173. Нажмите «Начать симуляцию», затем «Планшет ↗» у погрузчика. Примите задание, подтвердите забор по прибытии, затем доставку. Заказ должен завершиться на обоих экранах. Для второго водителя выберите R-02. Препятствие создаётся кнопкой «Проход передо мной перекрыт»; диспетчер открывает проходы обратно.

Проверки из корня проекта:

```bash
python3 -m unittest discover -s tests -v
cd frontend
npm run build
```

На момент передачи пройдены 5 проверок сценария и сборка frontend. Через интерфейс проверены принятие, забор, доставка, изменение маршрута и синхронизация планшета с диспетчерской панелью.

## Где работать

| Файл | Назначение |
|---|---|
| `backend/agents.py` | Выбор исполнителя, поиск маршрута BFS и блокировки зон. Основная точка входа участника №2. |
| `backend/simulation.py` | Состояние склада, цикл задания, резервирование, обработка команд и движение. |
| `backend/models.py` | Модели заказа, товара и техники. |
| `backend/main.py` | HTTP API и WebSocket. |
| `frontend/src/App.tsx` | Диспетчерский интерфейс и планшет водителя. |
| `tests/test_workflow.py` | Проверки жизненного цикла и ограничений. |
| `architecture.md` | Контракты и архитектура. |
| `project-plan.md` | Распределение ответственности и план на четыре периода. |

Названия `Robot`, `robots` и `/api/robots/...` сохранены ради совместимости. В текущем сценарии это виртуальные погрузчики с `kind: forklift`. Не переименовывайте их без согласованного изменения backend, frontend и документации.

Цикл исполнителя:
`idle → offered → to_pickup → confirm_pickup → to_dropoff → confirm_delivery → returning → idle`.

## Следующая задача участника №2

Первый отдельный результат — интерфейс принятия решений, подготовленный к последующему подключению LLM, с работающим детерминированным вариантом. Ранее договорились подключать LLM позже; ключи и платный сервис для этого этапа не нужны.

1. Отделить предложение плана от его применения. Вход: снимок задач, товара, ресурсов и ограничений. Выход: структурированное назначение с идентификаторами и коротким объяснением.
2. Перенести проверку любого предложения в явный серверный валидатор: существование объектов, доступность ресурса, текущая фаза, резерв, вместимость и достижимость.
3. Сохранить текущую политику назначения как вариант по умолчанию и будущий резерв при ошибках LLM.
4. Добавить объяснение решения в журнал: почему выбран именно этот исполнитель, почему предложен обход или ожидание.
5. Проверить недопустимое предложение и убедиться, что оно не меняет состояние. Сохранить прохождение существующих проверок.

Критерий готовности: текущая демонстрация работает, решения проходят единый контракт и проверку, в журнале видна причина назначения. Следующий этап с реальной LLM отдельно согласовать с командой: провайдер, модель, бюджет и настройка ключей.

LLM в целевой версии предлагает назначения и решения при конфликтах. Она не подтверждает доставку вместо водителя и не изменяет склад напрямую. Запросы к модели нельзя выполнять на каждом такте или блокировать ими цикл движения. Для будущего асинхронного ответа необходимо повторно проверять актуальность состояния перед применением плана.

## Ограничения, которые важно знать

- Перезапуск backend, в том числе autoreload при изменении Python-файла, сбрасывает склад.
- Нет базы данных, авторизации и проверки личности водителя. Выбор R-01/R-02 — демонстрационный переключатель.
- Нет WMS, сканера и реального позиционирования. Демонстрация проверена в двух вкладках одного компьютера; доступ с физического планшета отдельно не настроен.
- Грузоподъёмность условная, размеры клеток не в метрах. Динамика настоящего погрузчика не моделируется.
- Поиск маршрутов учитывает текущую занятость клеток. Гарантированное разрешение всех взаимных блокировок при произвольных сценариях ещё не реализовано.
- Статусы техники и товара обновляются обычным кодом. Существующие классы агентов не являются LLM-агентами.
