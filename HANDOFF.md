# Передача работы участнику №2

Рабочая ветка – `makar`. Эта инструкция заменяет прежний переход на `codex/participant-2-agents` от `origin/codex/team-handoff`. Получение копии и безопасная проверка ветки описаны в [README](README.md) и [CONTRIBUTING.md](CONTRIBUTING.md).

## Что передаётся

Симуляция с детерминированным назначением, BFS, временными перекрытиями, водительскими подтверждениями и конструктором склада. Текущий алгоритм и API описаны в [архитектуре](architecture.md), ограничения – в [состоянии проекта](docs/project-status.md). Запуск и тесты находятся в [DEVELOPMENT.md](DEVELOPMENT.md).

Реальная LLM не подключена. Объект предложения плана, единый валидатор таких предложений и механизм проверки асинхронного ответа пока отсутствуют. Это следующая задача, а не описание готовой инфраструктуры.

## Следующий результат по существующему плану

Следующие пункты сохраняют направление прежней передачи. Их реализация требует отдельной задачи на код; документационный аудит их не выполняет.

1. Определить снимок входа и структурированное предложение назначения: ID заказа, ресурса, причина выбора и сведения для проверки актуальности.
2. Отделить предложение от применения. Проверять существование и актуальность объектов, фазу, резерв, вместимость и достижимость до изменения состояния. Различать временное ожидание и недопустимое назначение.
3. Использовать существующий детерминированный алгоритм как первоначального поставщика предложений. Резерв при отказе внешнего поставщика понадобится только после его появления.
4. Записывать причину принятия/отклонения и выбора среди альтернатив, не выдавая числовую оценку за полное объяснение.
5. Проверить отказ без мутации, устаревшее и конкурирующее предложение, недостижимость и совместимость с пользовательскими макетами.

Критерий готовности: существующие сценарии продолжают работать, новое предложение проходит явную серверную проверку, отклонение не меняет состояние, результат воспроизводится тестом. Это будущие критерии приёмки, не отметка о выполнении.

## Границы изменения

Основные точки входа: [agents.py](backend/agents.py) и вызывающая его [simulation.py](backend/simulation.py). Модели, API, frontend и тесты образуют общий контракт.

Сохраняйте `Robot`, `robots`, `/api/robots/...`, водительские фазы и ручные подтверждения, пока их изменение не согласовано. Не считайте выбранный маршрут подтверждением доставки. Не предполагайте фиксированные размеры и две машины: конструктор уже входит в ветку.

Будущий внешний планировщик должен предлагать решения; проверка и применение остаются на backend. Асинхронный ответ потребуется проверять по актуальному состоянию. Провайдер, модель, бюджет и ключи LLM отдельно не определены и не требуются для первого этапа.

## Восстановление контекста

1. Прочитать [AGENTS.md](AGENTS.md) и проверить Git.
2. Сверить [контекст участника №2](docs/participant-2-context.md) с текущим кодом.
3. Выбрать проверки по задаче: для функциональных изменений проверить поведение, для документационных – факты, ссылки и состав изменений.
4. Продолжать конкретную задачу пользователя; если она уже задана, повторное подтверждение не требуется. Этот файл сам по себе не разрешает публикацию или расширение документационной задачи до изменения кода.
