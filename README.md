# Мультиагентная система управления складом и логистикой

Учебный веб-прототип для распределения заказов и моделирования перемещения грузов по клеточному складу. Диспетчер управляет симуляцией, а пользователь планшетного экрана принимает задание и подтверждает забор и доставку виртуального товара.

**Статус:** демонстрационная система с централизованным управлением и детерминированными ролями назначения, маршрутизации и учёта перекрытий. Самостоятельные процессы агентов, обмен сообщениями между ними, LLM и управление физической техникой не реализованы. Название отражает тему курсовой работы; степень реализации мультиагентного подхода раскрыта ниже.

## Что можно показать

* Назначение заказов свободным погрузчикам с учётом очереди приоритетов и условной вместимости.
* Резервирование товара, принятие задания, движение к товару, подтверждения забора и доставки, возвращение на стоянку.
* Построение маршрута BFS, ожидание при отсутствии пути и перестроение при перекрытии прохода.
* Диспетчерскую и планшет водителя с обновлением общего состояния через WebSocket.
* Конструктор карты с проверкой геометрии, импортом и экспортом JSON.

Начальная карта имеет размер 12 × 8, два погрузчика и три заказа. Пользовательский макет меняет размеры и число погрузчиков; после его применения заказы и товары отсутствуют до добавления нового заказа. Состояние хранится в памяти одного процесса.

## Как устроены роли

| Компонент | Реальное решение | Граница ответственности |
| --- | --- | --- |
| `ManagerAgent` | Фильтрует по свободной вместимости, выбирает исполнителя по оценке с расстоянием Манхэттена | Очередь приоритетов, резервирование и применение назначения выполняет симуляция |
| `RobotAgent` | Находит кратчайший путь по четырём направлениям для заданного снимка препятствий | Один общий объект планировщика обслуживает всю технику |
| `ZoneAgent` | Хранит временные перекрытия и проверяет допустимость закрываемой клетки | Не ведёт переговоры, очереди или разрешение взаимных блокировок |
| `WarehouseSimulation` | Вызывает роли, проверяет команды, меняет состояние и двигает технику | Центральный координатор, а не отдельный агент каждого погрузчика |

Роли взаимодействуют через обычные вызовы Python и общее состояние. Объект `Robot` хранит данные виртуального погрузчика, но не имеет собственного цикла принятия решений. Детерминированность сама по себе не исключает агентный подход; ограничение этого прототипа состоит в отсутствии самостоятельного поведения и протокола взаимодействия исполнителей.

На каждом такте симуляция последовательно рассматривает погрузчики по ID, пересчитывает пути с учётом текущей занятости и перемещает каждый максимум на одну клетку. Это предотвращает вход в занятую клетку в штатном цикле, но не гарантирует завершение всех заданий на произвольной карте. Общая оптимальность распределения не доказана.

Подробности алгоритмов, состояний и API: [архитектура](architecture.md).

## Быстрый запуск на Windows

Нужны Python 3.11+, Node.js с npm и доступ к пакетным реестрам для установки. Проверенное окружение: Python 3.11.9, Node.js 24.15.0, npm 11.12.1. Проект использует FastAPI, Pydantic, Uvicorn, React 19, TypeScript 5.7 и Vite 6.

Если репозиторий ещё не получен:

```powershell
git clone https://github.com/DestXXL/-multi-agent-warehouse-and-logistics-management-system.git warehouse-logistics
cd warehouse-logistics
```

Для существующей копии сначала проверьте ветку и изменения по [правилам совместной работы](CONTRIBUTING.md); повторное клонирование не требуется.

Первый терминал, из корня репозитория:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Второй терминал, также из корня:

```powershell
cd frontend
npm ci
npm run dev
```

Откройте [диспетчерскую](http://127.0.0.1:5173/?view=control). Backend должен работать одновременно с frontend. [Swagger UI](http://127.0.0.1:8000/docs) показывает HTTP API, [снимок склада](http://127.0.0.1:8000/api/state) позволяет проверить сервер.

Frontend обращается к имени хоста открытой страницы на порту 8000. Для локального показа используйте `127.0.0.1` в обеих вкладках. Инструкции для Linux/macOS, требования к портам и диагностика: [DEVELOPMENT.md](DEVELOPMENT.md).

## Демонстрация исходного склада

1. После свежего запуска backend нажмите «Начать симуляцию». ORD-001 получит R-01, ORD-002 – R-02; их товары будут зарезервированы. ORD-003 останется в очереди (`pending`). До принятия заданий техника не движется.
2. Откройте «Планшет ↗» у R-01 и нажмите «Принять задание».
3. Дождитесь прибытия и нажмите «Подтверждаю: товар забран». До подтверждения товар остаётся зарезервированным.
4. На пути к отгрузке можно нажать «Проход передо мной перекрыт», когда кнопка доступна. Система покажет обход либо ожидание; диспетчер может «Открыть проходы».
5. По прибытии подтвердите доставку. Заказ станет выполненным, товар получит новую позицию, погрузчик начнёт возвращение на стоянку.
6. Повторите действия для R-02 и следующего назначенного заказа. Следующий заказ назначается только свободному ресурсу после возвращения в `idle`. Выполненный заказ (`completed`) ещё не означает окончания возврата (`returning`); для окончания всей смены дождитесь возврата обоих погрузчиков.

Пауза останавливает такты движения, но допускает корректные водительские подтверждения. Индивидуальная остановка погрузчика блокирует его подтверждения до возобновления. «Сбросить склад» удаляет прогресс; при пользовательском макете сохраняет его геометрию. Для возврата к встроенному сценарию перезапустите backend.

Отдельный сценарий конструктора: [DEMO-LAYOUT.md](DEMO-LAYOUT.md).

## Проверка

Из корня, после установки окружения:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
npm --prefix frontend run build
```

В репозитории 10 тестов: пять для водительского цикла и пять для макетов/API. Сборка проверяет TypeScript и создаёт frontend в `frontend/dist/`. Автоматических тестов браузерного интерфейса и команд `npm test`/`npm run lint` нет. Результаты конкретного аудита и границы проверок: [отчёт](docs/documentation-audit.md).

## Ограничения и развитие

Текущие показатели интерфейса – число движущихся погрузчиков, незавершённых и завершённых заказов, номер такта. Измерений пропускной способности, времени ожидания, сравнений алгоритмов и доказанного выигрыша производительности нет.

Нет постоянного хранилища, авторизации, интеграций с WMS, сканерами и позиционированием. JSON сохраняет только геометрию. Клетки и вместимость не имеют физических единиц. Это среда для учебного показа, а не система безопасного управления реальным складом.

[Состояние проекта](docs/project-status.md) разделяет реализованное, частично реализованное и запланированное. [План](project-plan.md) сохраняет цели развития, включая контракт предложений, координацию и возможную LLM.
