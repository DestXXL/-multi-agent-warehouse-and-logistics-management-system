## Архитектура и стек

- Backend: Python 3.11+, FastAPI, Uvicorn, WebSocket. Зависимости runtime находятся в `backend/requirements.txt`.
- Frontend: React 19, TypeScript, Vite. `npm run build` запускает `tsc -b` и `vite build`.
- Источник истины о состоянии — один объект `WarehouseSimulation` в памяти процесса. Изменение состояния и фаз происходит на backend; UI отображает его и отправляет команды.
- При старте backend жизненный цикл FastAPI запускает фоновый цикл с шагом примерно в одну секунду. Изменения публикуются клиентам через `/ws/state`; первичный снимок доступен через `/api/state`.
- Интерфейс использует HTTP к хосту текущей страницы на порту 8000 и WebSocket. CORS ограничен локальными адресами frontend разработки (`localhost` и `127.0.0.1:5173`).
- Обработчики, тесты и модели синхронны и локальны для процесса. Никакого межпроцессного брокера или внешнего планировщика нет.

## Как работает существующий сценарий

После `reset` создаётся демонстрационная сетка 12×8 с препятствиями, точками забора и отгрузки, тремя товарами/заказами и двумя погрузчиками `R-01`, `R-02`. `start` запускает симуляцию и пытается назначить заказы.

Менеджер сортирует ожидающие заказы по приоритету, оценивает допустимых исполнителей по вместимости, доступности и расстоянию и выбирает исполнителя. Товар резервируется за заказом. Маршрутизатор строит путь BFS по четырём соседним клеткам, обходя препятствия, закрытые и занятые клетки.

Симуляция продвигает робота на одну клетку за такт. Водитель должен принять предложенное задание, подтвердить забор товара и подтвердить доставку. Только подтверждение доставки завершает заказ. После него погрузчик возвращается на домашнюю позицию. Оператор может ставить симуляцию на паузу, остановить/возобновить робота, создать демонстрационное затруднение, сообщить о препятствии и открыть проходы.

Товары, резервирования, роботы, заказы, фазы и журнал событий существуют только в памяти. Перезапуск backend сбрасывает демонстрационную конфигурацию. Журнал ограничен последними 100 событиями.

## Контракты между участниками

### Участник 1 — моя зона

`backend/models.py`, `backend/simulation.py`, `backend/agents.py` в части runtime-планирования и безопасности, `backend/main.py`, backend API, состояние, сценарий, правила допустимости и проверки команд. Нужен контроль сохранения API-полей и переходов водителя.

### Участник 2 — планирование/LLM

В проверенной ветке LLM и отдельного интеграционного интерфейса к ней нет. Будущий агент должен выдавать предложения о назначениях/маршрутах; он не должен напрямую мутировать состояние. Backend обязан перепроверять любое предложение перед исполнением. Таймаут, недоступность или некорректный ответ планировщика не должны останавливать такт симуляции или обходить безопасную детерминированную логику.

### Участник 3 — frontend

`frontend/src/App.tsx` потребляет `/api/state`, WebSocket `/ws/state`, отправляет команды API и показывает карту/заказы/погрузчики/журнал и подтверждения водителя. Согласовывать с frontend изменения формы состояния, идентификаторов, фаз и endpoint-ов. В `alex` нет редактора раскладки склада, который уже добавлен в более новом `main`; интеграция пользовательских карт должна учитывать его контракт.

### HTTP API, фактически найденный в `backend/main.py`

| Метод и путь | Назначение |
|---|---|
| `GET /api/state` | Полный снимок текущего состояния |
| `POST /api/simulation/start` | Запуск |
| `POST /api/simulation/pause` | Пауза |
| `POST /api/simulation/reset` | Сброс к демонстрационному складу |
| `POST /api/simulation/congestion` | Создание затруднения маршрута |
| `POST /api/robots/{robot_id}/driver-action` | Подтверждение водителя для заказа/этапа |
| `POST /api/robots/{robot_id}/obstacle` | Сообщить о препятствии по маршруту погрузчика |

## Проблемы и архитектурные риски

Приоритеты ниже — выводы аудита исходников, а не утверждение о подтверждённых авариях в эксплуатации.

### P1 — движение и безопасность

- BFS считает занятые клетки препятствиями, но система не резервирует клетки и временные интервалы для роботов. Такты обходятся последовательно; при конфликте робот может ждать, а при сложном расположении — возникнуть взаимная блокировка или длительное ожидание. Нет диспетчера трафика, обнаружения циклов ожидания, правил приоритета и гарантированного восстановления.
- Тест полного сценария доказывает отсутствие пересечения только для текущей фиксированной карты/заказов. Он не является доказательством безопасности для произвольной раскладки и динамических команд.
- Координатная клетка абстрактна: нет габаритов погрузчика, скорости/торможения, направления, зоны обзора, датчиков и временной неопределённости. Текущий путь нельзя показывать оператору реального погрузчика как физически безопасную навигацию.
- При сообщении о препятствии и восстановлении пути важно сохранять остановку оператором, корректную фазу и отсутствие входа в занятую/закрытую клетку. Эти инварианты следует расширить тестами на конфликтные сценарии.

### P1 — проверка данных и допустимых команд

- API создания заказа проверяет попадание координат в пределы карты и препятствия, но не реализует полноценную доменную проверку: допустимость точки как зоны забора/отгрузки, доступность пути, согласованность заказа с конкретным товаром и лимиты склада. Нужно определить контракт заказа и проверять его в едином доменном слое, а не только в HTTP-обработчике.
- Добавление заказа создаёт/связывает запас в памяти. Требуется определить поведение для дубликатов, отсутствующего товара, повторных запросов и заказа на уже зарезервированный/перемещённый товар.
- Поскольку API может принимать команды без авторизации, любой клиент локальной сети, имеющий доступ к backend, потенциально может менять состояние. Для учебного localhost-прототипа допустимо, для реального склада — нет.

### P2 — состояние, эксплуатация и масштабирование

- Состояние не переживает рестарт и не разделяется между несколькими backend-процессами. При запуске нескольких workers у каждого будет собственный склад, а WebSocket-клиенты могут получать разные состояния.
- Нет идентификатора симуляционного запуска/версии состояния для обнаружения устаревших команд кроме проверки текущего заказа/фазы в отдельных действиях.
- WebSocket транслирует состояние, но нет отдельного протокола версий/дельт, восстановления пропущенных событий и backpressure-политики.
- Цикл и операции пока рассчитаны на малый демонстрационный склад и несколько виртуальных погрузчиков; измерений производительности нет.

### P2 — поддерживаемость контрактов

- Документация `architecture.md` отстаёт от фактических endpoint-ов и отдельных полей состояния. Это повышает риск несовместимого изменения frontend и backend.
- Отдельные правила валидации распределены между API и симуляцией. Перед подключением LLM или layout editor следует закрепить единый контракт входного плана и безопасный исполнитель.
- Ветка `alex` отстаёт от актуальной истории `main` по коммитам документации и интеграции редактора карты. До слияния надо согласовать с командой способ и момент интеграции; здесь merge/rebase не выполнялся.

### Вне текущего прототипа

LLM, WMS/ERP, физические погрузчики, планшетная авторизация, пользовательские роли, БД, аудит операций и промышленный safety case не реализованы. Добавление LLM само по себе не сделает управление физической техникой безопасным. Для реальной площадки нужны отдельные аппаратные/системные контракты, независимые safety interlocks и поэтапная валидация.
