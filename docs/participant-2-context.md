## 1. Что реально работает

Приложение – демонстрационная симуляция клеточного склада 12 × 8 с двумя виртуальными погрузчиками, тремя исходными заказами, каталогом товаров, диспетчерской, планшетом выбранного водителя и журналом до 100 событий. Оператор запускает, останавливает и сбрасывает симуляцию, останавливает погрузчик и открывает проходы. Водитель принимает задачу, сообщает о перекрытии следующей клетки маршрута, подтверждает забор и доставку. Положение и маршрут рассылаются через WebSocket после команд и каждого такта. После доставки погрузчик возвращается на стоянку. Все данные исчезают при перезапуске backend.

Физические погрузчики, проверка личности водителя, WMS, сканер, реальная телеметрия, постоянное хранилище и LLM отсутствуют. Названия `Robot` и `/api/robots/...` относятся в текущем сценарии к виртуальным погрузчикам с `kind: forklift` и сохранены ради совместимости.

## 2. Карта компонентов и поток

```text
React App.tsx: диспетчерская и планшет
       │ POST команд / GET состояния        ↑ WebSocket полного состояния
       ▼                                    │
FastAPI main.py: маршруты API и рассылка ─┘
       │
       ▼
WarehouseSimulation: владелец Warehouse, фаз, резервов и журнала
       ├─ ManagerAgent.choose_robot → оценка кандидата
       ├─ RobotAgent.plan_route → BFS по клеткам
       └─ ZoneAgent.blocked_cells → временно закрытые проходы
```

`backend/models.py` задаёт `Warehouse`, `Order`, `StockItem`, `Robot` и сериализацию в JSON. `backend/simulation.py` вызывает роли синхронно, проверяет команды и непосредственно меняет состояние. `backend/main.py` хранит один глобальный экземпляр симуляции, запускает цикл с периодом 1 секунда и рассылает `simulation.state()`. WebSocket `/ws/state` сначала присылает снимок, затем целиком обновлённое состояние. Frontend также делает начальный `GET /api/state`, переподключает сокет при обрыве и блокирует кнопки команд без связи. Сервер не проверяет личность клиента.

### Цикл заказа

1. `start()` и затем каждый `tick()` вызывают `_assign_orders()`. Заказы `pending` сортируются по убыванию приоритета и идентификатору. Менеджер рассматривает только свободные, не остановленные ресурсы с достаточной условной вместимостью. Для конкретного заказа оценка = `priority × 10 − ManhattanDistance × 2 − itemLoad`; равенство разрешается по ID ресурса. Приоритет задаёт порядок обработки заказов, но при сравнении исполнителей одного заказа его вклад одинаков.
2. Симуляция устанавливает `order.robot_id`, `robot.order_id`, фазу `offered`, статус заказа `assigned`, `stock.status=reserved` и `reserved_by=order.id`; затем рассчитывает маршрут к забору. Маршрут заранее не является условием назначения.
3. `accept` переводит фазу в `to_pickup`. На каждом такте симуляция в порядке ID ресурсов заново планирует маршрут и делает не более одного шага. По прибытии фаза `confirm_pickup`, статус заказа `picking`; движения до подтверждения нет.
4. `pickup` допустим только при совпадении ID задания, фазе и координатах забора, действительном резерве и отсутствии остановки оператором. Товар становится `picked`, загрузка увеличивается, заказ переходит в `delivering`, ресурс едет к месту доставки. Во время движения координата товара следует за погрузчиком.
5. По прибытии фаза `confirm_delivery`; только `deliver` завершает заказ, переносит товар в точку назначения, снимает резерв и груз. Ресурс переходит в `returning`, освобождает отгрузку и затем становится `idle`. Пауза симуляции останавливает такты, но не запрещает подтверждение достигнутой операции.

`driver_action` отклоняет устаревший ID, неверную фазу, положение и остановленный ресурс; HTTP выдаёт 404 для отсутствующего ресурса и 409 для конфликтной команды. Отдельного серверного контракта для предложения агентного решения нет. Переходы обновляются обычным кодом, а не моделью LLM.

### Маршрут и координация

`RobotAgent.plan_route` применяет BFS к четырём ортогональным соседям и возвращает кратчайший по числу клеток путь без исходной клетки. Непроходимы стены/стеллажи, клетки из `ZoneAgent.blocked_cells` и текущие позиции других ресурсов. Планировщик не учитывает время, будущие позиции, размеры техники, ширину прохода, приоритет движения и стоимость поворотов. При отсутствии пути симуляция ставит `waiting` и повторяет поиск на следующем такте. При остановке оператором ресурс не движется.

Водительская команда `/obstacle` закрывает следующую незанятую клетку собственного маршрута, если она не является точкой забора или доставки его заказа. Диспетчерская `/simulation/congestion` выбирает клетку на пути, для которой есть более длинный обход. Симуляция перестраивает затронутые маршруты, увеличивает `route_version`, записывает длину обхода либо ожидание. `/aisles/reopen` снимает временные блокировки. Агент зоны только хранит набор перекрытий и проверяет границы/статическое препятствие; очередями и конфликтами между ресурсами он не управляет.

## 3. Фактическая мультиагентность и контракты

Три класса в `backend/agents.py` – детерминированные сервисные роли. `ManagerAgent` выбирает одного ресурса для заказа; `RobotAgent` – одна общая реализация BFS для всех ресурсов, а не независимый процесс на каждый погрузчик; `ZoneAgent` – набор перекрытых клеток. Они не обмениваются сообщениями и не владеют основным состоянием. Их последовательно вызывает `WarehouseSimulation`, которая принимает и применяет решения. Поэтому текущая реализация показывает разделение ролей, но ещё не автономное взаимодействие агентов.

Существующие контракты: модели `Order/Robot/StockItem/Warehouse`; вызовы `choose_robot(order,item,robots) → (robot,score)|None`, `plan_route(start,goal,width,height,blocked,occupied) → route|None`, `close_aisle(point,obstacles,width,height)`; HTTP команды и полный JSON снимок по WebSocket. Договорённость о структурированном предложении, серверном валидаторе и резервной детерминированной политике записана в `HANDOFF.md`, но в коде отсутствует. Сейчас нет отдельного объекта предложения, единой проверки предложений, версии снимка решения или механизма перепроверки асинхронного ответа. Журнал сообщает приоритет/числовую оценку назначения и длину обхода/ожидание, но не аргументы выбора относительно альтернатив.

Для будущей LLM безопасная граница – только предложение с ID объектов и краткой причиной, затем серверная проверка актуальности, резерва, вместимости, достижимости и фазы непосредственно перед применением. Подтверждение фактической операции остаётся за человеком или доверенной интеграцией. Вызов модели на каждом такте и прямое изменение `Warehouse` моделью не допускаются.

## 4. Конструктор из `origin/main`

В объединённой версии доступны `backend/layout.py`, `frontend/src/LayoutEditor.tsx`, `tests/test_layout.py`, `DEMO-LAYOUT.md` и три API: `GET /api/layout`, `POST /api/layout/validate`, `PUT /api/layout`. JSON версии 1 задаёт размер 4–40 × 4–30 и клетки `rack`, `wall`, `pickup`, `shipping`, `robot`, для стеллажа – 1–12 ярусов. Pydantic запрещает лишние поля, проверка требует рабочие точки, отсутствие пересечений, статическую связность и доступ к стеллажам. Применение разрешено до активной смены, атомарно сбрасывает задания, создаёт ресурсы по стоянкам и сохраняет выбранную геометрию при `reset`; перезапуск процесса возвращает исходную карту. Стены и стеллажи превращаются в прежний список `obstacles`, поэтому BFS и агентные классы не меняются. Ярусы служат метаданными, в маршрутизации не участвуют. Проверка статической связности не доказывает отсутствие динамических блокировок.

Конструктор пришёл из `origin/dan` через `origin/main` и теперь включён в `makar`. В агентной логике учитывайте новые размеры, число ресурсов и пустой список заказов после применения макета. Не предполагайте две машины, три заказа или постоянный размер 12 × 8 в агентном контракте.
