# Состояние реализации

Дата проверки – 15 октября 2026 года. Основание – исходники и тесты коммита `cf9949b`, ветка `makar`. Этот файл является единым реестром возможностей и ограничений. При изменении кода обновляйте статус по доказательствам, а не по названию задачи.

## Возможности

| Возможность | Состояние | Основание и граница |
| --- | --- | --- |
| Модель склада, товара и заказов | Реализовано | [models.py](../backend/models.py), состояние в памяти |
| Приоритетная очередь и выбор исполнителя | Реализовано | `_assign_orders()`, `ManagerAgent`; эвристика, без глобальной оптимизации |
| Резервирование и подтверждения | Реализовано | `driver_action()`, пять workflow-тестов; нет проверки личности водителя |
| BFS, перекрытие, ожидание и пересчёт | Реализовано | [agents.py](../backend/agents.py), [simulation.py](../backend/simulation.py) |
| Диспетчерская и планшет | Реализовано | [App.tsx](../frontend/src/App.tsx), общий снимок через WebSocket |
| Конструктор и JSON геометрии | Реализовано | [layout.py](../backend/layout.py), [LayoutEditor.tsx](../frontend/src/LayoutEditor.tsx), пять тестов |
| Мультиагентное взаимодействие | Частично реализовано | Выделены три сервисные роли; нет самостоятельных циклов исполнителей и сообщений |
| Разрешение конфликтов движения | Частично реализовано | Проверяется текущая занятость, возможен обход/ожидание; нет гарантии завершения |
| Объяснение решений | Частично реализовано | Журнал показывает приоритет, оценку и длину обхода/ожидание; сравнения альтернатив нет |
| Наблюдение за результатами | Частично реализовано | Счётчики и журнал есть; методика измерения эффективности отсутствует |
| Предложение плана и единый валидатор | Запланировано | [HANDOFF.md](../HANDOFF.md); типов и отдельной границы проверки пока нет |
| LLM и резерв при отказе внешнего поставщика | Запланировано | [project-plan.md](../project-plan.md); поставщика и вызовов API моделей нет |
| Типы исполнителей, допуски, разбиение заказов, переназначение | Запланировано | Цели исходного плана, текущими контрактами полностью не представлены |
| Физический склад, WMS, сканеры, позиционирование | Запланировано | Направление развития; внешние системы и интерфейсы не определены |

## Ограничения, требующие изменений кода или решений команды

Приоритеты ниже – оценка аудита для планирования, не утверждённая очередь команды.

| ID | Приоритет | Подтверждённое ограничение | Следствие |
| --- | --- | --- | --- |
| S1 | Высокий | `_assign_orders()` резервирует товар до поиска пути | Недостижимый заказ удерживает ресурс; ожидание не является доказательством выполнимости |
| S2 | Высокий | Нет отдельного предложения и единой проверки перед применением | Нельзя считать систему готовой к подключению внешних решений |
| S3 | Высокий | Последовательный BFS без временных резервов и протокола разъезда | Возможны взаимная блокировка и бесконечное ожидание |
| S4 | Средний | Расстояние Манхэттена вместо длины реального пути при назначении | Выбранный ресурс может иметь более длинный фактический маршрут |
| S5 | Средний | `_report_point()` исключает только рабочие точки собственного заказа | Возможно перекрытие точки другого заказа |
| S6 | Средний | `deliver` не повторяет проверку `stock.status/reserved_by` из `pickup` | Ограничение проверки, существенное при будущих интеграциях; штатные тесты проходят |
| S7 | Высокий для эксплуатации | Нет авторизации и разграничения ролей | Доступный клиент может отправить команду любого водителя; прототип не готов к реальному складу |
| S8 | Средний | Состояние и 100 событий хранятся в одном процессе | Перезапуск теряет данные, несколько workers не разделяют склад |
| S9 | Средний | Заказ создаёт новый товар, проверяет только границы/статические препятствия | Не обеспечены адресное складское хранение и проверка достижимости заказа |
| S10 | Средний | Фиксированные подписи «12 × 8», «2 узла»; стены выглядят как стеллажи | Отображение может расходиться с пользовательской геометрией |
| S11 | Низкий | После применения редактор предлагает добавление заказа в диспетчерской, где нет формы | Нужна кнопка демозаказа в конструкторе или API |
| S12 | Средний | Импорт использует исходный JSON после проверки, без нормализованного ответа Pydantic | При пропуске полей по умолчанию браузер может получить неполную модель; экспортируйте полный JSON |
| S13 | Средний | Нет автоматических браузерных тестов, сетевых WS-тестов и CI в репозитории | Успешные unit/API-тесты и сборка не покрывают весь интерфейс |
| S14 | Средний | Python-зависимости заданы диапазонами без lock-файла | Окружение новой установки может отличаться; версии проверенного запуска записаны в отчёте |
| S15 | Требует решения команды | Нет LICENSE | Условия распространения не оформлены; аудит лицензию не выбирает |

## Границы доказательств

Десять имеющихся тестов проверяют конкретные сценарии. Они не доказывают отсутствие всех конфликтов и не измеряют производительность. Успешная статическая валидация макета не означает, что произвольное число погрузчиков сможет завершить смену.

Система не имеет постоянного журнала аудита, физических габаритов, модели торможения и нормативов безопасности. Отсутствие этих механизмов не скрывается за названиями «интеллектуальная» или «мультиагентная».

Результаты установки, тестов, дополнительных опытов и редакторских проверок находятся в [отчёте аудита](documentation-audit.md). Следующие работы – в [плане](../project-plan.md) и [передаче №2](../HANDOFF.md).
