# Состояние проекта и план развития

Сверено с кодом 17 октября 2026 года на `f503f86`. Эксперименты ниже выполнены 15 октября на `cf9949b`; код backend, frontend и тестов между этими коммитами не менялся. Этот реестр отделяет наблюдаемое поведение от целей. Технические контракты находятся в [архитектуре](../architecture.md).

## 1. Реализованные возможности

* Модель склада, погрузчиков, товара и заказов хранится в памяти одного процесса – [models.py](../backend/models.py), [simulation.py](../backend/simulation.py).
* Симуляция сортирует очередь по приоритету и ID, выбирает свободный ресурс через `ManagerAgent`, резервирует товар и выполняет водительский цикл с ручными подтверждениями. Пять тестов [workflow](../tests/test_workflow.py) проверяют конкретные переходы.
* `RobotAgent` строит маршрут BFS по четырём направлениям; `ZoneAgent` хранит временные перекрытия. При отсутствии пути погрузчик ждёт, при изменении перекрытий путь обновляется.
* Диспетчерская и планшет получают полный снимок по WebSocket, отправляют действия через HTTP. [Конструктор](../frontend/src/LayoutEditor.tsx) проверяет карту, применяет её, импортирует и экспортирует JSON геометрии; пять [тестов макета](../tests/test_layout.py) проверяют часть API и смены.

## 2. Частично реализованные возможности

| Направление | Реальная граница |
| --- | --- |
| Мультиагентность | Три сервисные роли вызываются центральной симуляцией; самостоятельных циклов исполнителей и протокола сообщений нет |
| Координация движения | Текущая занятость учитывается при последовательном такте; будущие клетки не резервируются, завершение всех заданий не гарантировано |
| Объяснение решений | Журнал сообщает приоритет, оценку, обход или ожидание; сравнения альтернатив и полного объяснения нет |
| Наблюдение | Счётчики состояния и до 100 событий есть; методика и сбор метрик эффективности отсутствуют |

## 3. Известные ограничения и дефекты

Приоритеты – оценка для обсуждения командой, а не утверждённое расписание.

| ID | Приоритет | Подтверждённое ограничение и следствие |
| --- | --- | --- |
| S1 | Высокий | `_assign_orders()` назначает ресурс и резервирует товар до поиска пути; недостижимое задание удерживает оба |
| S2 | Высокий | Нет отдельного предложения плана и единого валидатора перед применением; внешний поставщик решений пока не подключаем безопасно |
| S3 | Высокий | Последовательный BFS учитывает текущую занятость без временных резервов и протокола разъезда; возможны взаимная блокировка и бесконечное ожидание |
| S4 | Средний | Для выбора ресурса используется расстояние Манхэттена, а не длина пути с препятствиями |
| S5 | Средний | `_report_point()` исключает рабочие точки лишь собственного заказа; можно перекрыть точку другого заказа |
| S6 | Средний | `deliver` не повторяет проверку `stock.status/reserved_by`, которая есть у `pickup`; это существенно для будущих интеграций |
| S7 | Высокий для эксплуатации | Нет авторизации и проверки личности водителя; доступный клиент может отправлять его команды |
| S8 | Средний | Склад и 100 последних событий существуют только в одном процессе; перезапуск теряет их, несколько workers не разделяют состояние |
| S9 | Средний | API заказа создаёт новый товар и проверяет лишь границы и статические препятствия; нет выбора SKU и проверки достижимости |
| S10 | Средний | Подписи «12 × 8», «2 узла» фиксированы; стены выглядят как стеллажи при пользовательской карте |
| S11 | Низкий | После применения макета сообщение предлагает добавить заказ в диспетчерской, где нет формы. Кнопка «Добавить демозаказ на склад» **уже есть в конструкторе**; требуется исправить подсказку и переход пользователя |
| S12 | Средний | Импорт браузера использует исходный JSON после серверной проверки, не нормализованный ответ Pydantic; файл с пропущенными defaults может дать неполную модель в редакторе |
| S13 | Средний | Нет автоматических браузерных, сетевых WebSocket тестов и CI; unit/API тесты и сборка покрывают не весь интерфейс |
| S14 | Средний | Python-зависимости заданы диапазонами без lock-файла; новая установка может дать иные версии |
| S15 | Решение команды | Нет LICENSE; условия распространения не оформлены |

### Доказательства и пределы проверок

15 октября 2026 года в Windows на `cf9949b` прошли 10 из 10 тестов и сборка frontend. В отдельном HTTP-опыте были созданы заказ и резерв, затем выполнены принятие, забор, доставка и возврат за 12 тактов; это результат одного небольшого сценария, не метрика производительности. Проверены ответы 404/409/422, отказ применить ошибочный макет без мутации состояния, начальный и обновлённый снимки WebSocket. Небольшой JSON 4 × 4 из [сценария конструктора](../DEMO-LAYOUT.md) прошёл серверную проверку и применение. Среда и команды для повторения основных проверок – в [DEVELOPMENT.md](../DEVELOPMENT.md).

Для S1 отдельный опыт закрыл выходы обоим погрузчикам: оба заказа остались назначенными, а товары зарезервированными без доступного пути. Для S3 синтетический узкий коридор с двумя встречными возвратами оставил оба ресурса в ожидании после 20 тактов. Фикстуры этих двух опытов в репозитории не сохранены; кодовые причины видны в `_assign_orders()` и `tick()` [симуляции](../backend/simulation.py). Опыты подтверждают существование проблемы, но не частоту её возникновения на произвольных картах.

Автотесты не доказывают отсутствия всех конфликтов. Тест пользовательского макета повторно применяет геометрию исходного склада; отдельного теста изолированного стеллажа нет. Полный цикл кнопок в браузере, Linux/macOS и физический планшет при аудите не проверялись. Статическая связность карты не гарантирует динамический разъезд. Для эксплуатации также отсутствуют постоянный аудит, физические габариты и нормативы безопасности.

## 4. Запланированные функции

Первый технический шаг – отделить структурированное предложение назначения от серверной проверки и применения, сохранив детерминированную политику. До мутации серверу нужно проверять актуальность заказа и ресурса, фазу, резерв, вместимость и достижимость; отказ должен оставлять состояние неизменным. Проверки должны покрыть устаревшее или конкурирующее предложение и недостижимый путь. Затем обсуждаются координация конфликтов, типы ресурсов и допуски, декомпозиция заказов, ручное переназначение и отделение планов от фактов. Это цели – текущие модели и API их полностью не поддерживают. Подробности – в [плане изменений назначения](assignment-plan.md).

LLM рассматривается как возможный будущий поставщик предложений и объяснений, но для мультиагентности не обязателен. Провайдер, модель, бюджет, формат доступа, таймауты, качество и проверка устаревшего асинхронного ответа ещё не определены. Физический склад, WMS, сканеры и позиционирование также остаются направлениями развития без согласованных внешних интерфейсов.

Для оценки эффективности сначала нужно зафиксировать макеты, заказы, последовательность подтверждений и сравниваемые политики. Возможные показатели – такты до завершения, пройденные клетки, ожидание, завершённые заказы и отклонённые планы. Сбор этих показателей и сравнение пока не реализованы.

## 5. Этапы и приоритеты команды

Области работ №1 – модель, симуляция и API; №2 – агенты, планирование и координация; №3 – интерфейс и интеграция. Изменения общих контрактов согласуются по [правилам совместной разработки](../CONTRIBUTING.md). Четыре периода исходного плана задают относительную последовательность; календарные сроки и факт завершения периода не утверждены.

| Период | Основная работа | Проверяемый результат |
| --- | --- | --- |
| 1, недели 1–2 | Модель склада, роли, формат назначений и каркас интерфейса | Общий сценарий и согласованные контракты |
| 2, недели 3–4 | Движение, резервы, подтверждения, предложения с проверкой, планшет | Полный цикл заказа и отклонение недопустимого действия |
| 3, недели 5–6 | Ограничения ресурсов, координация конфликтов и объяснения; LLM только после отдельного решения | Воспроизводимый конфликт с объяснением и границами разрешения |
| 4, недели 7–8 | Повторяемые сценарии, отказы внешнего планировщика при его появлении, сравнение политик и итоговый показ | Проверки, демонстрация и согласованная документация |

Ближайший приоритет для развития – безопасная граница принятия решения и проверка предложения до мутации. После неё можно оценивать координацию конфликтов; подключение внешнего поставщика требует отдельного решения. Расширенный показ должен различать допустимое и отклонённое предложение, конфликт ресурсов, причины обхода или ожидания и резервную политику при отказе поставщика, если он будет добавлен.

В исходных материалах указана работа Сажиной Ю. В., Липинского Л. В. и Свиридовой А. С. «Многоагентная система управления складскими перемещениями», 2017, т. 2, с. 173–175. [Страница статьи](https://cyberleninka.ru/article/n/mnogoagentnaya-sistema-upravleniya-skladskimi-peremescheniyami) при проверке 15 октября была закрыта проверкой доступа; библиографические сведения и связь конкретных алгоритмов с полным текстом независимо не подтверждены.
